PR #14228: local seccomp precompile follow-up (2026-11-12)

Status: measurement report recorded before publication. See README.md for the published commits and post-rebase validation.
Baseline: cd7d4251b17357d8f1004dbb3d82bd4a086cc89c (published PR head).
Candidate: baseline + fix.patch; no unrelated main-branch rebase.
Review: https://github.com/google/gvisor/pull/14228#discussion_r4540405313

Finding and scope
Ayush's report is correct. FilestoreReflink participates in ConfigKey but was
missing from optionsToPrecompile. All 576 previously generated configurations
had reflink disabled. Enabling the feature therefore selected the synchronous
runtime BPF build/optimization fallback during sandbox creation and restore.
This is a startup-performance defect, not evidence of a snapshot-integrity or
permission-isolation defect. It belongs in #14228 because the flag is introduced
by that PR.

The production fix adds nine lines using the existing option-expansion pattern.
Every previously supported configuration now has both reflink settings. No
runtime permission rule changes, prewrite, asynchronous park or new modes are
introduced. ConfigKey still separates enabled and disabled filters. Options
already unsupported by precompilation retain their existing fallback behavior.

Deterministic reproduction and regression tests
- tests-only.patch fails on the published PR: 576/576 missing counterparts;
  all four enabled lookup cases fail (systrap/KVM x DirectFS off/on).
- After the fix, all 1,152 unique configurations have their opposite flag setting.
  Full config_test passes, including serial/parallel deterministic generation.
- The generated-release filter test passes eight configurations. It performs
  GetPrecompiled + RenderInstructions and interprets the actual generated BPF:
  valid FICLONE is permitted only when enabled; negative destination/source FDs
  remain denied. There were no opt-test skips. Fastbuild explicitly skips this
  generated-filter test because precompilation is intentionally disabled there;
  the configuration-enumeration test still applies.
- Formal container regression: systrap and KVM, three repetitions; 54 external
  checkpoint/restore cases, including 24 reordered-mount cases, all pass.
  Ordinary checkpoint/resume, split-FS and snapshot failure-cleanup cases in
  the recorded test filter also pass; no skipped cases.
- 48/48 performance trials verify all 64 MiB of the restored snapshot and the
  resumed source, including rejection of the opposite content version. In all
  trials the original starts writing again before checkpoint CLI return.
- Source startup logs independently show fallback before the fix and successful
  precompiled loading afterward; no fallback remains in the candidate trials.
- Complete opt release build, make DOCKER_BUILD=false lint, lint-cc and nine
  harness tests pass. Initial lint-cc used stale compilation-database paths;
  regenerating the database fixed the environment and all 367 sources passed.

Measurement methodology
Intel Xeon Platinum 8269CY, amd64, same host and XFS; 24 alternating pairs on
both sides. Existing BenchmarkSandboxBoot runs all systrap/KVM and overlay
subcases, both reflink flag settings, five boots per sample. Boot means active
sentry boot (process start to kernel start excluding the wait for the OCI start
signal), not whole CLI time. The same small benchmark-only configuration hook
is applied to both sides and kept out of fix.patch.

External checkpoint/restore uses a 64 MiB newly dirty layer, --leave-running,
and no prewrite on BOTH sides. Source debug logging is enabled for pause/phase
measurement. Timed restore uses --debug=false on both sides to exclude the old
fallback's debug dump of 576 keys. Checkpoint CLI already waits for durability;
DurableCheckpoint includes the same extra harness fsync verification on both
sides. Both sides use matching complete release filesets. Baseline files are
byte-identical to the previously tested release for published cd7d4251b.

Performance summary (median, milliseconds; before -> after)
- Reflink enabled kvm active boot: 75.25 -> 67.28; sample SD 2.31 -> 1.71, n=24 each.
- Reflink enabled kvm_overlay active boot: 75.88 -> 69.06; sample SD 2.24 -> 2.17, n=24 each.
- Reflink enabled systrap active boot: 36.49 -> 27.08; sample SD 0.97 -> 0.93, n=24 each.
- Reflink enabled systrap_overlay active boot: 37.38 -> 27.69; sample SD 0.83 -> 1.05, n=24 each.
All four enabled Boot differences have p<0.001. The corresponding Loader.Run
phase improves; loader creation does not show a significant difference.
All 12 primary Boot/New/Run metrics with reflink disabled show no statistically
significant difference. This does not establish zero overhead or cold-cache
behavior. Full raw tables and all secondary percentile metrics follow below.

- External pause_ms: 64.00 -> 63.21; sample SD 2.14 -> 2.46, n=24 each.
- External cli_ms: 72.57 -> 71.77; sample SD 2.45 -> 2.53, n=24 each.
- External durable_ms: 74.46 -> 73.94; sample SD 2.47 -> 2.50, n=24 each.
- External restore_cli_ms: 75.31 -> 67.54; sample SD 2.67 -> 2.87, n=24 each.
Restore improves by 10.32% (p<0.001). Application pause (p=0.185), checkpoint CLI
(p=0.159), complete persistence verification (p=0.351), and FICLONE (p=0.519)
do not show significant differences. The log-derived pause window alone has a
small p=0.036 difference; the application heartbeat measurement and unchanged
clone path do not support claiming a checkpoint-pause optimization. Sample SD
is recorded in boot-statistics.json and performance-summary.json; benchstat's
printed +/- intervals are confidence intervals, not sample SD.

Binary-size cost (file bytes, not RSS)
- program_count: 576 -> 1,152; delta 576 (100.00%).
- generated_go_bytes: 20,597,828 -> 41,286,271; delta 20,688,443 (100.44%).
- release_file_bytes: 188,418,932 -> 192,736,692; delta 4,317,760 (2.29%).
- gvisor_sentry: 55,379,043 -> 59,696,803 bytes; +4.12 MiB (7.80%).
All other release files are byte-identical, including runsc. The generated Go
source is a build artifact, not checked-in source. The whole release grows by
2.29%, while sentry alone grows by 7.80%. Repeated startup tests do not measure
the cold-page-cache or resident-memory effect of this size increase. The review's
6.29-6.43 ms / 3.81 MB figures refer to its isolated runtime compilation benchmark;
this follow-up measures end-to-end startup phases and restore CLI, not that
allocation microbenchmark.

Assessment
Use the explicit option expansion in #14228. It preserves the existing precompile
architecture and opt-in security boundary, has a small production diff, and
removes a measured startup/restore penalty at a quantified +4.12 MiB complete
release cost. Avoid adding a new runtime-parameterized permission mechanism
solely to reduce variant count in this PR. This fix does not address the first
fully dirty layer's FICLONE writeback delay; that tradeoff remains unchanged.
